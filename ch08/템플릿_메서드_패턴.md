# 디자인패턴 - 템플릿 메서드 패턴

## 템플릿 메서드 패턴이란?

> 알고리즘의 전체 흐름은 상위 클래스가 **확정**하고, 그 흐름 안에서 달라지는 세부 단계만 하위 클래스가 채워넣는 패턴.
> - 신입사원 온보딩 과정
>   - 서류 제출 및 공통 교육
>   - 장비 수령
>   - **부서별 교육 → 전체 흐름에서 달라지는 부분**
>   - 최종 팀 배정

- SOLID 원칙과의 연결
  - OCP → 알고리즘의 전체 골격은 불변이지만 세부 단계는 상속을 통해서 확장에 열려있다.
  - DIP → 상위 클래스는 구체적인 구현이 아닌 자신이 선언한 추상 메서드에 의존.

## 템플릿 메서드 패턴을 적용하기 이전의 코드의 문제

```java
public class Coffee {

    // 커피 제조 전체 과정
    public void prepareRecipe() {
        boilWater();
        brewCoffeeGrinds();
        pourInCup();
        addSugarAndMilk();
    }

    private void boilWater() {
        System.out.println("물을 끓입니다.");
    }

    private void brewCoffeeGrinds() {
        System.out.println("필터로 커피를 우려냅니다.");
    }

    private void pourInCup() {
        System.out.println("컵에 따릅니다.");
    }

    private void addSugarAndMilk() {
        System.out.println("설탕과 우유를 추가합니다.");
    }
}

public class Tea {

    // 홍차 제조 전체 과정
    public void prepareRecipe() {
        boilWater();
        steepTeaBag();
        pourInCup();
        addLemon();
    }

    private void boilWater() {
        System.out.println("물을 끓입니다.");
    }

    private void steepTeaBag() {
        System.out.println("찻잎을 우려냅니다.");
    }

    private void pourInCup() {
        System.out.println("컵에 따릅니다.");
    }

    private void addLemon() {
        System.out.println("레몬을 추가합니다.");
    }
}
```

| 단계 | Coffee | Tea | 동일 여부 |
|------|--------|-----|----------|
| 1단계 | `boilWater()` | `boilWater()` | **동일** |
| 2단계 | `brewCoffeeGrinds()` | `steepTeaBag()` | 다름 |
| 3단계 | `pourInCup()` | `pourInCup()` | **동일** |
| 4단계 | `addSugarAndMilk()` | `addLemon()` | 다름 |

- 동일한 코드의 중복이 많다.
  - `boilWater()` , `pourInCup()` 이라는 동일 로직이 클래스 수 만큼 복제.
  - 음료의 개수가 추가될 수록 요구사항 변경에 동일한 수정을 많이 반복하는 고생길 Open
- 알고리즘의 순서 보장이 없다.
  - `prepareRecipe()`의 4단계는 논리적으로 반드시 지켜져야 한다. 그런데 각 클래스가 이 순서를 독립적으로 구현하면 실수로 순서를 바꾸거나 단계를 빠뜨릴 위험이 있다.
- 다형성 활용이 불가능하다.
  ```java
  if (beverageType.equals("coffee")) {
      new Coffee().prepareRecipe();
  } else if (beverageType.equals("tea")) {
      new Tea().prepareRecipe();
  } else if (beverageType.equals("greenTea")) {
      new GreenTea().prepareRecipe();
  }
  ```

- 결국 세 가지 문제의 근본 원인은 변하지 않는 부분과 변하는 부분이 분리되지 않고 각 클래스 안에 뒤섞여 있어서 발생한다. 템플릿 메서드 패턴은 이를 정확히 분리하는 패턴이다.

## 템플릿 메서드 패턴을 구현하는 방법

```java
public abstract class CaffeineBeverage {

    // 템플릿 메서드: 알고리즘의 골격을 확정
    // final로 선언하여 하위 클래스가 이 순서를 변경하지 못하게 보호
    public final void prepareRecipe() {
        boilWater();        // 공통 단계
        brew();             // 추상 메서드 → 하위 클래스가 구현
        pourInCup();        // 공통 단계
        addCondiments();    // 추상 메서드 → 하위 클래스가 구현
    }

    // 공통 단계: 모든 음료에 동일한 로직
    // private으로 선언하여 하위 클래스가 임의로 바꿀 수 없도록 강제
    private void boilWater() {
        System.out.println("물을 95도로 끓입니다.");
    }

    private void pourInCup() {
        System.out.println("컵에 따릅니다.");
    }

    // 추상 메서드: 하위 클래스가 반드시 채워야 하는 "변하는 부분"
    // protected로 선언하여 외부에는 노출하지 않되, 하위 클래스는 접근 가능.
    protected abstract void brew();
    protected abstract void addCondiments();
}
```

- 이 클래스 하나로 **코드 중복이 제거**되었고 **알고리즘의 순서가 강제**되었다.

```java
public class Coffee extends CaffeineBeverage {

    @Override
    protected void brew() {
        System.out.println("필터로 커피를 우려냅니다.");
    }

    @Override
    protected void addCondiments() {
        System.out.println("설탕과 우유를 추가합니다.");
    }
}

public class Tea extends CaffeineBeverage {

    @Override
    protected void brew() {
        System.out.println("찻잎을 우려냅니다.");
    }

    @Override
    protected void addCondiments() {
        System.out.println("레몬을 추가합니다.");
    }
}

// 실제 사용 시 아래처럼 사용
// if-else 분기 없이 공통 타입으로 처리 -> 다형성 문제 해결!
CaffeineBeverage beverage = createBeverage(beverageType);
beverage.prepareRecipe();  // 어떤 음료든 동일한 인터페이스로 호출
```

### Hook 메서드를 통한 선택적 확장

- 음료를 만들 경우, 어떤 고객은 첨가물을 원할 수도 있고, 어떤 고객은 첨가물을 원하지 않을 수 있다.
- 이때 템플릿 메서드를 정의한 상위 클래스에서 `addCondiments()`를 아예 건너 뛰고 싶을 수 있다.
- 이 문제를 Hook 메서드로 해결할 수 있음.

```java
public abstract class CaffeineBeverage {

    public final void prepareRecipe() {
        boilWater();
        brew();
        pourInCup();
        // hook 메서드로 조건부 실행을 구현
        if(customerWantsCondiments()){
            addCondiments();
        }
    }

    private void boilWater() {
        System.out.println("물을 95도로 끓입니다.");
    }

    private void pourInCup() {
        System.out.println("컵에 따릅니다.");
    }

    protected abstract void brew();
    protected abstract void addCondiments();

    // Hook 메서드 -> 하위 클래스가 선택적으로 오버라이드한다. 강제가 아닌 선택.
    protected boolean customerWantsCondiments(){
        return true;
    }
}
```

## 템플릿 메서드 패턴을 구현할 때 주의 사항

- 템플릿 메서드에는 반드시 `final`을 지정해서 누군가의 실수를 방지한다.
- 공통 단계는 `private`, 추상 메서드는 `protected abstract`, Hook 메서드에는 `protected` 제한 필수.
- 너무 많은 추상 메서드를 만들지 마라
  - 이 경우에는 패턴이 오히려 짐이 된다. 정말 모든 하위 클래스가 추상 메서드를 구현해야하는가?
  - 너무 많은 추상 메서드를 만들었다면, 정말로 변하는 부분인지에 대한 식별이 잘 되지 않았을 가능성이 높다.

## 템플릿 메서드 패턴의 실제 적용 사례

- 템플릿 메서드 패턴을 스프링에서 적용한 사례의 대표적인 것은 `JdbcTemplate`, `TransactionTemplate`, `RestTemplate` , `AbstractPlatformTransactionManager` 등등
- 이전의 코드에서는 변하는 부분을 채우는 것을 '상속'을 사용했다. 하지만 Spring의 `XXXTemplate` 클래스들은 함수형 인터페이스로 채웠다.
- 사실 엄밀한 템플릿 메서드 패턴을 그대로 차용한 것들은 거의 찾아보기 힘듦

```java
@Override
@Nullable
public <T> T execute(ConnectionCallback<T> action) throws DataAccessException {
    Assert.notNull(action, "Callback object must not be null");

    Connection con = DataSourceUtils.getConnection(obtainDataSource());
    try {
        // Create close-suppressing Connection proxy, also preparing returned Statements.
        Connection conToUse = createConnectionProxy(con);
        return action.doInConnection(conToUse);
    }
    catch (SQLException ex) {
        // Release Connection early, to avoid potential connection pool deadlock
        // in the case when the exception translator hasn't been initialized yet.
        String sql = getSql(action);
        DataSourceUtils.releaseConnection(con, getDataSource());
        con = null;
        throw translateException("ConnectionCallback", sql, ex);
    }
    finally {
        DataSourceUtils.releaseConnection(con, getDataSource());
    }
}

@Override
@Nullable
public <T> T execute(TransactionCallback<T> action) throws TransactionException {
    Assert.state(this.transactionManager != null, "No PlatformTransactionManager set");

    if (this.transactionManager instanceof CallbackPreferringPlatformTransactionManager cpptm) {
        return cpptm.execute(this, action);
    }
    else {
        TransactionStatus status = this.transactionManager.getTransaction(this);
        T result;
        try {
            result = action.doInTransaction(status);
        }
        catch (RuntimeException | Error ex) {
            // Transactional code threw application exception -> rollback
            rollbackOnException(status, ex);
            throw ex;
        }
        catch (Throwable ex) {
            // Transactional code threw unexpected exception -> rollback
            rollbackOnException(status, ex);
            throw new UndeclaredThrowableException(ex, "TransactionCallback threw undeclared checked exception");
        }
        this.transactionManager.commit(status);
        return result;
    }
}
```

## 템플릿 메서드 패턴의 한계

- '상속'을 사용하기 때문에, 결국 상속이 가지는 문제점을 그대로 떠안는다.
- 단일 상속의 제약이 있다. 음료 예시에서 `CaffeineBeverage`를 상속받은 커피나 차는 다른 클래스를 상속 받을 수 없다.
- 하위 클래스에서 상위 클래스의 변경을 인지할 수 없다. 하위 클래스가 적다면 문제 없지만 엄청나게 많다면 상위 클래스의 변경이 예측하기 어려운 사이드 이펙트를 만들 수 있다.
- 또한 런타임에 유연하지 않다. 템플릿 메서드 패턴은 변하는 부분의 내용은 클래스 정의 시점에 확정되는데 Coffee 클래스의 `brew()` 는 항상 필터로 커피를 우려낸다.
  ```java
  CaffeineBeverage coffee = new Coffee();

  // 첫 번째 호출: 커피를 우려냅니다
  coffee.prepareRecipe();

  // 두 번째 호출에서 brew()의 동작만 바꾸고 싶다면?
  // → 불가능
  coffee.prepareRecipe();
  ```

## 전략 패턴과 템플릿 메서드 패턴 비교

- 두 패턴은 같은 문제를 다른 방식으로 푼다. **변하지 않는 부분과 변하는 부분을 분리하는 것**에서 시작
- 템플릿 메서드는 상속으로, 전략 패턴은 조합으로 분리

```java
// 상위 클래스: 골격 + 빈칸
public abstract class CaffeineBeverage {

    public final void prepareRecipe() {
        boilWater();
        brew();             // 빈칸
        pourInCup();
        addCondiments();    // 빈칸
    }

    private void boilWater() { System.out.println("물을 끓입니다."); }
    private void pourInCup() { System.out.println("컵에 따릅니다."); }

    protected abstract void brew();
    protected abstract void addCondiments();
}

// 하위 클래스: 빈칸을 상속으로 채움
public class Coffee extends CaffeineBeverage {
    @Override
    protected void brew() { System.out.println("커피를 우려냅니다."); }
    @Override
    protected void addCondiments() { System.out.println("설탕과 우유를 추가합니다."); }
}

// ── 사용 ──
CaffeineBeverage coffee = new Coffee();
coffee.prepareRecipe();
```

```java
// 전략 인터페이스: "빈칸"의 형태를 정의
@FunctionalInterface
public interface BrewStrategy {
    void brew();
}

@FunctionalInterface
public interface CondimentStrategy {
    void addCondiments();
}

// 컨텍스트 클래스: 골격 + 전략을 주입받음
public class CaffeineBeverage {

    private final BrewStrategy brewStrategy;
    private final CondimentStrategy condimentStrategy;

    public CaffeineBeverage(BrewStrategy brewStrategy,
                            CondimentStrategy condimentStrategy) {
        this.brewStrategy = brewStrategy;
        this.condimentStrategy = condimentStrategy;
    }

    public void prepareRecipe() {
        boilWater();
        brewStrategy.brew();                  // 주입된 전략 실행
        pourInCup();
        condimentStrategy.addCondiments();    // 주입된 전략 실행
    }

    private void boilWater() { System.out.println("물을 끓입니다."); }
    private void pourInCup() { System.out.println("컵에 따릅니다."); }
}

// 사용: 조합으로 음료를 구성
CaffeineBeverage coffee = new CaffeineBeverage(
    () -> System.out.println("커피를 우려냅니다."),
    () -> System.out.println("설탕과 우유를 추가합니다.")
);
coffee.prepareRecipe();
```

- 전략 패턴에서는 단일 상속 제약이 해소된다.
- 런타임 유연성을 확보할 수 있다.

### 그렇다면 두 패턴 중 무엇을 선택할 지에 대한 판단은?

- 템플릿 메서드가 더 적합한 경우
  - 빈칸들이 서로 강하게 연관되어 있는 경우
  - 빈칸의 내용이 한 번 정해지면 고정되며, 잘못된 조합을 컴파일 타임에 방지하고 싶은 경우
- 전략 패턴이 더 적합한 경우
  - 런타임에서 유연성이 필요한 경우
  - 변형이 조합의 많아 클래스 폭발이 우려되는 경우
  - 단위 테스트에서 각 빈칸을 독립적으로 검증하고 싶은 경우
